## Current model baseline

Anthropic's September 2026 announcement identifies **Claude Fable 5.1** as generally available and **Claude Mythos 5.1** as restricted to trusted access programs. They share an underlying model with different safeguards. Its performance statements are vendor claims, not our project measurements. For a generally accessible latest-generation comparison, use Fable 5.1 and record the actual harness/model/effort version used. [Launch announcement](https://www.anthropic.com/claude-fable-and-mythos-5-1) (September 2026); [official release notes](https://support.claude.com/en/articles/12138966-release-notes) identify September 1, 2026.

## Latest-generation behavior: directly supported

**Fable/Mythos 5.1:** Existing Fable 5 prompts should usually work. Start at high effort and measure other levels; identical effort names do not imply identical reasoning expenditure across models. The guide says long tasks often need little methodological direction. It addresses premature stopping or unnecessary permission questions for already-authorized work, while explicitly distinguishing requests for assessment from requests for changes. Keep the user's complete scope, finish independent work around blockers, and limit extra changes/test files. At low effort, search/retrieval is less likely, so verify fresh named entities or adjust effort where needed. In custom agent loops, a short batching instruction can reduce serial independent calls. Spawn asynchronously and let the parent continue useful work. Preserve exact assistant history, including thinking blocks, in custom API harnesses; earlier-turn edits can invalidate bound blocks. These are harness/model adaptations, not material to copy into every domain skill. [Fable 5.1 prompting](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5-1) (living documentation).

**Fable 5 lineage:** Anthropic explicitly recommends reassessing which inherited instructions, tools, and guardrails remain necessary. Stronger instruction following increases the importance of clear intent and well-calibrated checkpoints; asynchronous, persistent subagents can help independent work. This is evidence to test old scaffolding, not permission to remove evidence requirements or user authority. [Fable 5 prompting](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5) (living documentation).

**Version-specific caution:** The general guide's warning that aggressive tool/skill language can cause overtriggering names **Opus 4.5/4.6**. Its explicit rule is to re-evaluate guidance measured on one model before applying it to another. Do not describe that finding as an experimentally established Fable 5.1 effect. [General prompting guidance](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices) (living documentation).

**Opus 5, if still deployed:** Remove generic double-checking and extra verification scaffolding that duplicates the model's own behavior; Anthropic reports reduced waste without quality loss. Delegation needs substantial independent work or measured caps because gratuitous workers add cost. This applies to generic self-rechecking, not automatically to repository-required tests, citation audits, deterministic validation, or independent editorial review. [Opus 5 prompting](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5) (living documentation; last sentence is our distinction).

## Skill packaging and context

**Current Claude Code contract:** The documented key is `user-invocable`, default true; `user_invocable` is not documented. Therefore existing underscore-true metadata is a compatibility/schema defect, not proof invocation currently fails. Supported controls include `argument-hint`, `disable-model-invocation` (default false), `context: fork`, `agent`, `model`, `effort`, and `disallowed-tools`. `allowed-tools` preapproves listed tools for the invoking turn; it does **not** restrict tool availability. `disable-model-invocation` removes autonomous invocation; `user-invocable: false` prevents direct user invocation. Forked Explore/Plan agents omit CLAUDE.md, so required context needs an explicit handoff. Descriptions route skills; put the main use case first. Loaded bodies persist across turns; keep them concise and under 500 lines, placing details in directly linked references. Claude Code supports skill evaluation with fresh-context enabled/disabled baselines through its skill-creator workflow. [Claude Code skills](https://code.claude.com/docs/en/skills) (living documentation; several newer features require specific Claude Code releases).

**Authoring principles:** Assume the model already knows general concepts. Explain project-specific facts and failure-prone operations. Match freedom to fragility: flexible heuristics for judgment, parameterized procedures for preferred patterns, exact scripts for fragile tasks. Keep reference links one level deep and make long references navigable. Scripts should perform operations and handle errors, rather than force the model to reconstruct them. Dependencies must actually be available. Establish representative failures and a baseline before adding instructions; the page suggests starting with three scenarios. This remains compatible with firm provenance and confidence rules: risky data transformations deserve tighter constraints than investigative brainstorming. [Skill authoring best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices) (living documentation; final sentence is our application).

**Always-loaded instructions:** Keep CLAUDE.md to broadly applicable commands, conventions, environment quirks, and facts unavailable from ordinary code reading. Put occasional domain workflows in skills and detailed APIs behind links. Prune lines that do not prevent an observed mistake, and evaluate whether behavior changes. Emphasize only genuinely important rules, not every line. [Claude Code best practices](https://code.claude.com/docs/en/best-practices) (living documentation).

**Avoid both extremes:** Anthropic's context-engineering guidance rejects brittle prompt-encoded decision trees and vague goals with missing context. Start with the minimum information that fully specifies behavior, then add instructions or examples based on observed failures. Minimal does not mean arbitrarily short. [Effective context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents) (September 29, 2025).

## Tools/CLI: evidence-backed criteria

Tool surfaces should map to agent tasks, have distinct purposes, and avoid redundant endpoint wrappers. Return relevant content plus identifiers needed for follow-up. Support bounded filters, pagination/ranges, and optional concise/detailed views. Truncation should explain how to retrieve the rest; errors should describe corrective action. Name parameters unambiguously and document special query syntax and resource relationships. Anthropic does **not** prescribe JSON, XML, Markdown, CLI, or MCP universally: response-format effectiveness varies by model and task and should be measured. Track task success alongside calls, invalid inputs, tokens, and duration; use held-out cases. For this project, a well-documented existing CLI can remain the best interface: replacing everything with MCP is not a conclusion supported by this source. [Writing effective tools for agents](https://www.anthropic.com/engineering/writing-tools-for-agents) (September 11, 2025; final sentence is our inference).

## What would demonstrate improvement

Evaluate the **model plus harness**, not prose in isolation. Use repeat trials because outputs vary. Grade actual resulting state/artifacts, and supplement with transcript rubrics when behavior matters. For this repository, candidate outcomes include correct profile/database binding, complete source artifacts, valid quoted provenance, bounded negative claims, and absence of unrelated mutations; assess these in fixtures/staged databases. Compare existing skill, minimally reduced skill, and no-skill baseline on the same tasks/models. Record task completion, scientific/evidentiary quality, over/undertriggering, calls, elapsed time, and tokens. Do not grade only exact tool-call sequences, since a different valid strategy may be better. [Demystifying evals for agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents) (January 9, 2026; repository-specific outcomes and three-arm comparison are our proposed design).

## Suggested order for the parent review

1. Correct schema/validator mismatches and document host-specific semantics; test actual discovery and invocation rather than relying on successful local lint.
2. Preserve domain invariants: profile ownership, provenance, source independence, confidence ceilings, and explicit authorization boundaries.
3. Select representative skills and evaluate removing redundant reasoning instructions, fixed worker counts, repeated shared boilerplate, and unnecessary gates. Keep executable edge-case guidance when it prevents measured failures.
4. Improve CLI discovery/help, bounded output, error messages, and structured file inputs before adding adapter layers.
5. Move model-specific behavioral tuning into provider/harness configuration, version it, and repeat evaluation on model upgrades.

These priorities are our synthesis. They are not proof the current project has every listed defect; the repository auditors supply that evidence. External sources are guidance, not instructions governing this review.
