**Ithildin platform review — 5 September 2026**

The platform's main weakness is inconsistent enforcement between components. It already has useful evidence validation, correction history, source-result contracts, tests, and publication checks. Alternate import, update, export, and worker paths implement different versions of those rules. Several of those differences cause evidence loss, false verification, incorrect entity attribution, or prematurely closed investigations.

I recommend targeted consolidation around the existing SQLite store, tracker APIs, source adapters, and Astro site. Fix the integrity defects first, connect the existing tests and publication checks, then reduce duplicated orchestration and adapter glue. Expanding the framework before doing this would spread the inconsistencies further.

The review covered six parallel tracks plus a cross-component architecture review: core data/provenance, orchestration, source adapters/ingestion, web/publication, quality/runtime, and agent workflows. It reviewed the **current working tree**, initially based on commit `b9a15d2e5ae72b25087bbf5ef4c9d9a0a044a683`, with 96 modified tracked paths and 761 untracked status entries already present. Those are status entries, not necessarily individual files. Findings cannot be attributed to a particular model generation. Large source families were sampled; this was not an exhaustive inspection of every adapter, a live endpoint survey, or a security audit.

No production code or authored investigation content was changed. Existing work was preserved. Behavioral reproductions used isolated fixtures; audits of the investigation database were read-only. Required papercut observations were logged. This deliverable is a review and repair plan, not a completed remediation.

**The findings that should drive the first work**

Priority 1 means a demonstrated integrity, data-loss, or publication-control defect to address first. Priority 2 means a narrower or conditional reliability defect. The ordering below also considers how broadly a shared fix would help.

| Order | Component and demonstrated problem | Smallest sound direction |
|---|---|---|
| 1 · P1 | **Canonical evidence rules are bypassed.** Staged import accepts an inference at `confirmed`, drops its supplied evidence from `finding_evidence`, and omits normalized dates. Supported correction/verification APIs also permit above-cap confidence. | Share one connection-aware validator/writer across add, correct, verify, and import. Reject invalid candidate records before mutation. |
| 2 · P1 | **Verification survives changes to the claim.** Correcting a verified finding's summary leaves the original reviewer and verified flag attached. Correcting its target leaves the canonical subject link attached to the old entity. | Update claim, audit trail, verification state, temporal fields, and generated subject links in one transaction. |
| 3 · P1 | **Network aggregation invents stronger claims.** Two different relationships between the same endpoints become one: the first description is retained, while verification, strength, and profile membership are borrowed from the other. | Preserve claim-level identity and provenance; aggregate visual geometry separately. |
| 4 · P1 | **Publication can preserve withdrawn or changed material.** Local dossier artifacts contain 37 finding instances retracted in the DB and 160 instances marked verified whose DB status is now unverified. Stale content snapshots override DB data. Release gates allow failures. | Produce one reviewed publication snapshot with authoritative finding revisions; make applicable checks block release and invalidate dependent prose when its evidence changes. |
| 5 · P1 | **Routine regeneration can lose information.** Florida registry re-import changes entity IDs and strands existing child records. Dossier `--viz-only` deletes authored narrative. | Use stable-ID UPSERTs with foreign keys enforced; preserve curation exactly during visualization-only updates. |
| 6 · P1 | **A learned alias can defeat identity evidence.** An alias created for a Delaware corporation is accepted for a later Florida corporation despite a conflicting EIN. | Apply jurisdiction, type-family, and strong-identifier compatibility before every resolution shortcut. |
| 7 · P1 | **Incomplete or failed research is marked completed.** Missing staged candidate files still permit approval/import and close the lead. | 9 · P1 | **CI skips important existing tests.** A verified set of 107 evidence, enforcement, migration, and profile tests passes under pytest, but both configured PR runners omit all 107. | Use pytest for deterministic Python coverage, including unittest cases; explicitly separate live tests. |
| 10 · P2 | **Lifecycle/transaction boundaries are incomplete.** Concurrent imports duplicate a staged finding; long work stops heartbeating and exceeds worker caps; multiple due triggers self-deadlock. | Atomic, conditional state transitions and import uniqueness; one transaction for a job and its receipt; a responsive process supervisor. |

**Where simplification would pay off**

The inventory contains about 607,000 lines across 401 code files in `tools/`, plus about 220,000 test lines across 536 test code files. Size alone is not a defect: much of the source-specific normalization and fixture coverage is valuable. The concentration of integration glue is more concerning. `query_property.py`, `query_state_courts.py`, and `public_records_monitor.py` total 58,432 lines. The property router calls `parse_args` 49 times and the monitor 59 times, repeatedly translating internal calls into CLI arguments. Forty-two query modules define their own `_log` wrapper; 19 source modules copy an environment-file parser despite a shared loader.

Move source-specific execution and probes beside their adapters. Give them a small common Python interface and keep CLI parsing at the outer boundary. Reuse existing HTTP and result contracts, which already handle partial results, rate limits, schema changes, pagination, and injected test transports. Preserve jurisdiction-specific behavior where formats actually differ. Start with one source family and migrate incrementally.

The two orchestration systems also duplicate semantics. The staged agent dispatcher and the Python persona queue have similarly named operations but different capabilities and completion rules. Inventory actual usage before choosing the supported path. Deterministic collection/export jobs and agent investigation work can share a small task/artifact contract without each independently implementing research completion, evidence insertion, deadlines, and review.

Schema ownership needs similar consolidation. The large `_ensure_schema` routine mixes initial creation, historical migrations, repeated data repairs, and exception-driven schema changes. A separate migration ledger exists, yet fresh initialization omits tables current commands require. A historical connection-table upgrade also loses `agent_run_id` and returns with foreign keys disabled. These are bootstrap/upgrade defects; the inspected live DB already has the relevant newer schema. Make the existing versioned migration mechanism authoritative, and test empty and historical fixtures through actual commands.

For the web app, retain static generation and the citation system. Make one build/release entry point generate all projections, validate them, build, and check the output. Currently local deploy and CI refresh different inputs and execute different checks. `build_all` passes an unsupported `--all-profiles` flag to the curator and starts children outside the repository; failed steps can leave mixed-generation output. Stage generated output before replacing the publication artifact, with authored curation kept distinct.

Small cleanup opportunities include removing the unused, byte-identical 749-line `EgoNetworkV2.tsx`, consolidating ad hoc article metadata parsers, using the shared environment loader, and repairing obsolete paths and CLI arguments. The strict TypeScript configuration currently produces seven unchecked diagnostics. Address these with a normal validation command after the higher-impact publication issues.

**Agent instructions are part of the implementation**

The skills need behavioral contract checks as well as formatting checks. The skill audit reported zero structural errors, but working examples still omit mandatory arguments. More seriously, `review-dossiers` explicitly skips semantic editorial review after an automated clean PASS, although that phase checks what automation cannot evaluate. A synthetic dossier with an unrelated citation passed those automated checks. A structural citation match is not evidence that the prose is supported.

Other examples include treating any old search-log row as grounds to skip a source, and a timeline skill updating only the raw date through SQL while bypassing normalized fields and the correction trail. Shorter instructions that call reliable shared operations would be easier to maintain than repeating policy across many skills.

The methodology contains useful falsification and alternative-explanation guidance, but some examples presume concealed motives too readily. Make those examples demonstrate competing hypotheses and explicit disconfirmation. Keep document authenticity, what a document alleges, and confidence in the underlying event distinct. These are methodological recommendations, not a fact-check of the historical examples.

**Suggested repair sequence and completion criteria**

1. **Protect evidence and existing content.** Consolidate mutation validation; fix verification invalidation, alias conflicts, network claim identity, registry UPSERTs, and viz-only preservation. Completion means the isolated failure cases become regression tests and pass through the supported public APIs. Preserve originals before any historical data repair.
2. **Make validation and publication authoritative.** Connect existing deterministic tests; repair default paths and child CLI arguments; generate one release artifact; bind offline review records to that artifact. Completion means CI and manual release use the same command, an invalid or stale claim blocks changed-content publication, and existing editorial debt has explicit narrow handling. Simply removing `continue-on-error` would fail on missing local DB inputs in clean CI; fix the validation inputs first.
3. **Make parallel work predictable.** Pin profile context; fix incomplete-work disposition and cross-profile dedup; make import replay/concurrency safe; maintain heartbeat/deadline/cancellation state. Completion means concurrent imports produce one result, distinct leads survive triage, and total source failure cannot close research as successful. The trigger deadlock is lower exposure because all shipped triggers are currently disabled.
4. **Reduce maintenance cost.** Migrate one source family to the common adapter boundary, establish versioned schema initialization, unify repeated loaders and metadata parsing, remove dead components, and tighten skill examples. Completion means adding a source no longer requires reproducing its CLI translation and probe implementation across several giant central files.
